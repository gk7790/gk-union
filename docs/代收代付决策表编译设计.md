# 代收代付决策表编译设计

## 设计结论

旧表暂时不动，只新增三张发布态决策表：

```text
1. payment_plan_catalog
2. payment_plan_bucket
3. payment_plan_route_option
```

旧表继续作为源配置和交易事实表：

```text
merchant_fee_rule      商户费率源配置
psp_route_rule         PSP路由源配置
psp_fee_rule           PSP成本源配置
psp_provider           PSP三方资源
psp_method             PSP方式资源
psp_account            PSP账户资源
pay_order              代收订单事实表
payout_order           代付订单事实表
```

新三张表只做“发布后的运行时决策表”。商户 API 优先读取 ACTIVE 决策表；没有 ACTIVE 决策表时，可以临时降级到旧实时规则，保证迁移不影响现有业务。

## 三张表关系

```text
payment_plan_catalog
一版已发布的支付方案

  1 对多

payment_plan_bucket
这一版方案里的金额区间 + 商户费率

  1 对多

payment_plan_route_option
这个金额区间下可选的 PSP 候选路由 + PSP 成本
```

例子：

```text
catalog:
  tenant_id = 1
  merchant_id = 2
  merchant_app_id = 3
  direction = PAYIN
  country_code = ''
  currency = PHP
  method_code = MAYA
  version = 5
  status = ACTIVE

bucket:
  0 <= amount < 1000
  merchant_fee_rule_id = 101

route options:
  PSP_A priority=1 weight=70 fallback_order=1
  PSP_B priority=1 weight=30 fallback_order=2
  PSP_C priority=2 weight=0  fallback_order=3
```

这样可以同时解决：

- 一个金额段多个 PSP 都可用。
- 按优先级选择 PSP。
- 同优先级按权重分流。
- PSP 出问题后跳过不可用 option。
- 提交失败后按 fallback_order 切备用 PSP。

## 核心原则

1. 配置表是源数据，决策表是发布产物。
2. 后台修改配置不直接影响线上交易。
3. 线上交易只读取 ACTIVE 决策表。
4. 同一维度只能有一个 ACTIVE catalog。
5. 金额只命中一个 bucket；如果命中 0 个或多个，说明发布数据异常。
6. 一个 bucket 可以有多个 route option。
7. PSP 密钥不进入三张计划表，也不进入 Redis。
8. 订单表旧结构暂时不动，继续保存现有规则和 PSP 快照字段。

## 发布维度

`payment_plan_catalog` 的唯一业务维度：

```text
tenant_id
merchant_id
merchant_app_id
direction
country_code
currency
method_code
version
```

说明：

- `direction`：`PAYIN` 代收，`PAYOUT` 代付。
- `country_code`：代收不用国家时统一保存空字符串 `''`；代付需要国家时保存实际国家编码。
- `merchant_app_id`：不区分应用时保存 `0`。
- `version`：同一维度下每次发布递增。
- `status`：`STAGING / ACTIVE / RETIRED`。

## 表结构

### payment_plan_catalog

保存一版发布后的支付决策表头。

```sql
CREATE TABLE `payment_plan_catalog` (
  `id` bigint NOT NULL COMMENT '主键ID',
  `tenant_id` bigint NOT NULL COMMENT '租户ID',
  `merchant_id` bigint NOT NULL COMMENT '商户ID',
  `merchant_app_id` bigint NOT NULL DEFAULT 0 COMMENT '商户应用ID; 不区分应用时为0',
  `direction` varchar(32) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '交易方向: PAYIN/PAYOUT',
  `country_code` varchar(32) COLLATE utf8mb4_unicode_ci NOT NULL DEFAULT '' COMMENT '国家编码; 无国家维度时为空字符串',
  `currency` varchar(16) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '币种',
  `method_code` varchar(64) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '支付/出款方式编码',
  `version` bigint NOT NULL COMMENT '配置版本号',
  `status` varchar(32) COLLATE utf8mb4_unicode_ci NOT NULL COMMENT '状态: STAGING/ACTIVE/RETIRED',
  `bucket_count` int NOT NULL DEFAULT 0 COMMENT '金额决策桶数量',
  `route_option_count` int NOT NULL DEFAULT 0 COMMENT '路由候选数量',
  `config_hash` varchar(128) COLLATE utf8mb4_unicode_ci DEFAULT NULL COMMENT '参与编译配置的哈希值',
  `compiled_at` datetime(3) NOT NULL COMMENT '编译时间',
  `activated_at` datetime(3) DEFAULT NULL COMMENT '激活时间',
  `remark` varchar(512) COLLATE utf8mb4_unicode_ci DEFAULT NULL COMMENT '备注',
  `created_by` bigint DEFAULT NULL COMMENT '创建人ID',
  `created_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updated_by` bigint DEFAULT NULL COMMENT '更新人ID',
  `updated_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_payment_plan_catalog_version` (`tenant_id`, `merchant_id`, `merchant_app_id`, `direction`, `country_code`, `currency`, `method_code`, `version`),
  KEY `idx_payment_plan_catalog_active` (`tenant_id`, `merchant_id`, `merchant_app_id`, `direction`, `country_code`, `currency`, `method_code`, `status`),
  KEY `idx_payment_plan_catalog_created` (`tenant_id`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='支付决策表头';
```

### payment_plan_bucket

保存 catalog 下的金额区间和商户费率命中结果。

```sql
CREATE TABLE `payment_plan_bucket` (
  `id` bigint NOT NULL COMMENT '主键ID',
  `tenant_id` bigint NOT NULL COMMENT '租户ID',
  `catalog_id` bigint NOT NULL COMMENT '支付决策表ID',
  `bucket_start_amount` decimal(24,8) NOT NULL COMMENT '金额区间开始，包含',
  `bucket_end_amount` decimal(24,8) DEFAULT NULL COMMENT '金额区间结束，不包含; NULL表示无上限',
  `merchant_fee_rule_id` bigint NOT NULL COMMENT '商户费率规则ID',
  `merchant_fee_snapshot_json` json DEFAULT NULL COMMENT '商户费率规则快照',
  `sort` int NOT NULL DEFAULT 0 COMMENT '桶排序',
  `created_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_payment_plan_bucket_catalog` (`tenant_id`, `catalog_id`, `sort`),
  KEY `idx_payment_plan_bucket_amount` (`tenant_id`, `catalog_id`, `bucket_start_amount`, `bucket_end_amount`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='支付决策金额桶';
```

金额区间使用半开区间：

```text
[bucket_start_amount, bucket_end_amount)
```

例如：

```text
0 <= amount < 1000
1000 <= amount < 5000
5000 <= amount
```

运行时如果一个金额命中多条 bucket，必须报配置冲突；不能 `findFirst` 随便选一条。

### payment_plan_route_option

保存某个金额 bucket 下的 PSP 候选路由。

```sql
CREATE TABLE `payment_plan_route_option` (
  `id` bigint NOT NULL COMMENT '主键ID',
  `tenant_id` bigint NOT NULL COMMENT '租户ID',
  `catalog_id` bigint NOT NULL COMMENT '支付决策表ID',
  `bucket_id` bigint NOT NULL COMMENT '金额桶ID',
  `route_rule_id` bigint NOT NULL COMMENT 'PSP路由规则ID',

  `psp_id` bigint NOT NULL COMMENT 'PSP Provider ID',
  `psp_code` varchar(64) COLLATE utf8mb4_unicode_ci DEFAULT NULL COMMENT 'PSP编码快照',
  `psp_method_id` bigint NOT NULL COMMENT 'PSP支付/出款方式ID',
  `psp_method_code` varchar(64) COLLATE utf8mb4_unicode_ci DEFAULT NULL COMMENT 'PSP支付/出款方式编码快照',
  `psp_account_id` bigint NOT NULL COMMENT 'PSP账户ID',
  `psp_account_no` varchar(128) COLLATE utf8mb4_unicode_ci DEFAULT NULL COMMENT 'PSP账户编号快照',

  `psp_fee_rule_id` bigint DEFAULT NULL COMMENT 'PSP成本费率规则ID',
  `psp_fee_snapshot_json` json DEFAULT NULL COMMENT 'PSP成本费率规则快照',

  `priority` int NOT NULL DEFAULT 100 COMMENT '优先级，数字越小越优先',
  `weight` int NOT NULL DEFAULT 100 COMMENT '同优先级下权重',
  `fallback_order` int NOT NULL DEFAULT 100 COMMENT '失败后的备用顺序',
  `status` varchar(32) COLLATE utf8mb4_unicode_ci NOT NULL DEFAULT 'ACTIVE' COMMENT '状态: ACTIVE/DISABLED',
  `sort` int NOT NULL DEFAULT 0 COMMENT '展示排序',
  `created_at` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',

  PRIMARY KEY (`id`),
  KEY `idx_payment_plan_route_bucket` (`tenant_id`, `bucket_id`, `status`, `priority`, `fallback_order`),
  KEY `idx_payment_plan_route_catalog` (`tenant_id`, `catalog_id`, `bucket_id`, `sort`),
  KEY `idx_payment_plan_route_psp` (`tenant_id`, `psp_id`, `psp_account_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='支付决策PSP候选路由';
```

说明：

- `payment_plan_route_option` 才是真正保存 PSP 候选的地方。
- `payment_plan_bucket` 不保存 PSP 字段，避免一个金额段多个 PSP 时结构冲突。
- `psp_fee_rule_id` 和 `psp_fee_snapshot_json` 跟 PSP 候选绑定，所以放在 route option。
- PSP 密钥不保存到 route option；运行时仍通过 `psp_account_id` 读取 `psp_account`。

## 发布流程

后台配置修改后不直接生效。

推荐流程：

```text
1. 保存配置
2. 点击测试/预检
3. 系统读取 merchant_fee_rule、psp_route_rule、psp_fee_rule、psp_provider、psp_method、psp_account
4. 检查金额区间、商户费率、PSP候选、PSP成本是否完整
5. 编译 STAGING catalog
6. 写入 bucket
7. 写入 route option
8. 同一事务把旧 ACTIVE 改为 RETIRED
9. 同一事务把新 STAGING 改为 ACTIVE
10. 清 Redis active key
```

同一维度发布时必须加事务和锁，避免出现两个 ACTIVE。

```sql
SELECT id
FROM payment_plan_catalog
WHERE tenant_id = ?
  AND merchant_id = ?
  AND merchant_app_id = ?
  AND direction = ?
  AND country_code = ?
  AND currency = ?
  AND method_code = ?
  AND status = 'ACTIVE'
FOR UPDATE;
```

然后执行：

```text
旧 ACTIVE -> RETIRED
新 STAGING -> ACTIVE
```

## 运行时选择逻辑

商户 API 运行时：

```text
1. 根据 tenant、merchant、app、direction、country、currency、method 读取 ACTIVE catalog
2. 根据 amount 命中唯一 bucket
3. 查询 bucket 下 ACTIVE route options
4. 过滤不可用 PSP Provider / PSP Method / PSP Account
5. 过滤 Redis 中紧急停用或熔断的 PSP / PSP Account
6. 按 priority 分组
7. 同 priority 下按 weight 选择
8. 提交 PSP
9. 如果提交失败，按 fallback_order 尝试下一个 option
```

银行卡代付需要额外处理银行匹配：

```text
1. 商户 API 入参 payee.bank_code 使用系统统一银行编码
2. payout_order.payee_bank_code 保存系统统一银行编码
3. route option 初选后，用 payee_bank_code 查询 psp_bank_mapping
4. 找不到映射的 route option 视为该 PSP 不支持该银行，直接过滤
5. 找到映射后，提交 PSP 前把系统银行编码转换成 PSP 银行编码
```

也就是：

```text
商户传入：系统银行编码
系统订单保存：系统银行编码
路由过滤：系统银行编码
提交 PSP：PSP 银行编码
```

不要把银行编码放进 `payment_plan_catalog` 主维度。原因是银行数量较多，如果按银行拆 catalog，会导致发布数据和 Redis key 膨胀。

如果没有 ACTIVE catalog：

```text
迁移阶段可以降级旧实时规则
完全切换后应直接报配置未发布
```

## 银行编码转换

银行卡代付时，商户 APP 侧使用系统统一银行编码，例如 `BDO`、`BPI`。

不同 PSP 对同一家银行可能使用不同编码，因此提交 PSP 前必须通过 `psp_bank_mapping` 转换。

推荐流程：

```text
1. 商户提交代付请求，payee.bank_code = 系统银行编码
2. 系统校验并保存 payout_order.payee_bank_code = 系统银行编码
3. 运行时命中 catalog、bucket、route options
4. 对每个 route option 查询 psp_bank_mapping
5. 找不到映射：过滤该 option
6. 找到映射：保留该 option，并记录 PSP 银行编码
7. 最终选中 option 后，adapter 请求使用 PSP 银行编码
```

匹配建议：

```sql
SELECT *
FROM psp_bank_mapping
WHERE tenant_id = ?
  AND psp_id = ?
  AND psp_method_id = ?
  AND system_bank_code = ?
  AND status = 1
LIMIT 1;
```

如果现有字段名不是 `system_bank_code` 和 `psp_bank_code`，也建议保持这个语义：

```text
平台统一银行编码
PSP侧银行编码
```

订单表只保存平台统一银行编码，不建议保存 PSP 银行编码。因为同一笔代付如果故障切换到另一个 PSP，PSP 银行编码可能不同。

银行维度不进入三张计划表主结构：

```text
payment_plan_catalog 不加 bank_code
payment_plan_bucket 不加 bank_code
payment_plan_route_option 不强制加 bank_code
```

除非后续出现更复杂需求：

```text
不同银行影响 PSP 路由优先级
不同银行影响 PSP 成本费率
不同银行有不同限额
不同银行要做独立健康状态
```

那时可以在 `payment_plan_route_option` 增加银行分组字段，例如：

```text
bank_match_mode
bank_group_code
```

当前阶段先用 `psp_bank_mapping` 做运行时过滤和编码转换，最简单，也最稳。

## PSP 故障停用

如果某个 PSP 出问题：

```text
1. 后台停用 psp_provider 或 psp_account
2. 写 Redis 紧急停用 key
3. 商户 API 运行时过滤该 PSP / Account
4. 自动选择下一个 route option
5. 后台后续重新发布 catalog，把故障 PSP 从新版本中移除
```

推荐 Redis key：

```text
payment:psp:disable:{tenantId}:{direction}:{pspId}
payment:psp-account:disable:{tenantId}:{direction}:{pspAccountId}
payment:psp:health:{tenantId}:{direction}:{pspId}
```

DB 状态负责最终一致，Redis 负责快速生效。

## 最优缓存方案

缓存采用三层：

```text
DB：最终可信数据
Redis：跨服务共享缓存和实时状态
本地缓存：5 到 10 秒热点加速
```

核心原则：

```text
静态发布态数据整体缓存
实时停用/健康状态单独缓存
Redis 不作为唯一数据源
Redis 丢失后可以从 DB 三张表回源
```

### 静态 ACTIVE Plan 缓存

当前不加 `payment_config_version`，直接缓存 ACTIVE plan 整体对象：

```text
payment:plan:active:{tenantId}:{merchantId}:{merchantAppId}:{direction}:{countryCode}:{currency}:{methodCode}
```

缓存内容包含：

```text
catalog
buckets
buckets.routeOptions
```

也就是 Redis 一个 key 缓存完整运行时决策对象，不要拆成 catalog、bucket、route_option 多个 key。

推荐 value 结构：

```json
{
  "catalog": {
    "id": 100,
    "version": 5,
    "status": "ACTIVE"
  },
  "buckets": [
    {
      "id": 1,
      "startAmount": "0",
      "endAmount": "1000",
      "merchantFeeRuleId": 101,
      "merchantFeeSnapshotJson": "{}",
      "routeOptions": [
        {
          "id": 11,
          "routeRuleId": 201,
          "pspId": 1,
          "pspCode": "PSP_A",
          "pspMethodId": 301,
          "pspMethodCode": "MAYA",
          "pspAccountId": 401,
          "pspAccountNo": "A001",
          "pspFeeRuleId": 501,
          "pspFeeSnapshotJson": "{}",
          "priority": 1,
          "weight": 70,
          "fallbackOrder": 1,
          "status": "ACTIVE"
        }
      ]
    }
  ]
}
```

不包含：

```text
PSP api_secret
PSP callback_secret
商户 api_secret
任何私钥
```

不要分别缓存：

```text
payment:plan:catalog:xxx
payment:plan:buckets:xxx
payment:plan:route-options:xxx
```

原因：

```text
减少 Redis 请求次数
避免 catalog、bucket、route_option 版本不一致
降低发布清理和运行时拼装复杂度
```

### PSP 紧急停用缓存

PSP 或 PSP Account 出问题时，需要比重新发布更快地生效。

推荐 Redis key：

```text
payment:psp:disable:{tenantId}:{direction}:{pspId}
payment:psp-account:disable:{tenantId}:{direction}:{pspAccountId}
```

推荐 value：

```json
{
  "disabled": true,
  "reason": "PSP timeout",
  "operatorId": "1",
  "expireAt": "2026-06-22T12:00:00"
}
```

说明：

```text
DB 状态负责最终一致
Redis disable key 负责秒级生效
TTL 可以设置 10 分钟到 2 小时
也可以后台手动解除
```

### PSP 健康状态缓存

健康状态由监控、请求统计或熔断组件写入。

推荐 Redis key：

```text
payment:psp:health:{tenantId}:{direction}:{pspId}
payment:psp-account:health:{tenantId}:{direction}:{pspAccountId}
```

推荐 value：

```json
{
  "status": "HEALTHY",
  "successRate": "0.98",
  "avgCostMs": 320,
  "windowSeconds": 60,
  "updatedAt": "2026-06-22T10:30:00"
}
```

运行时可按策略处理：

```text
DOWN：直接跳过
DEGRADED：有其他可用 option 时跳过，没有其他 option 时可按策略兜底
HEALTHY：正常参与选择
```

### 本地缓存

商户 API 服务本地也缓存完整 ACTIVE plan 对象。

推荐：

```text
local key：同 Redis active plan key
TTL：5 到 10 秒
```

作用：

```text
避免高频订单每次都访问 Redis
允许发布后几秒内自然刷新
```

如果发布后要求马上生效，后续可以通过 MQ、Redis Pub/Sub 或应用内事件通知商户 API 清理本地缓存。

### 缓存读取顺序

运行时读取顺序：

```text
1. 本地缓存读取 ACTIVE plan
2. 本地未命中读取 Redis ACTIVE plan
3. Redis 未命中读取 DB 三张表
4. DB 回源后回填 Redis 和本地缓存
5. 根据 amount 命中唯一 bucket
6. 读取 bucket.routeOptions
7. 过滤 option.status != ACTIVE
8. 读取 Redis disable/health 状态，过滤不可用 PSP / PSP Account
9. priority 最小优先
10. 同 priority 按 weight 选择
11. PSP 提交失败时按 fallback_order 尝试下一个 option
```

### 缓存发布清理

发布成功后：

```text
1. DB 写入 catalog/bucket/route_option
2. 旧 ACTIVE -> RETIRED
3. 新 STAGING -> ACTIVE
4. 删除 payment:plan:active:{...}
5. 可选：预热新 ACTIVE plan 到 Redis
6. 可选：通知商户 API 清本地缓存
```

PSP 紧急停用时：

```text
1. 写 DB 状态或运营停用记录
2. 写 Redis disable key
3. 商户 API 运行时立即过滤对应 PSP / Account
4. 后续重新发布，把故障 PSP 从新的 ACTIVE plan 中移除
```

最终效果：

```text
Plan 缓存负责快
disable/health 缓存负责实时
DB 三张表负责最终一致
```


发布产物表：

```text

```

交易事实表：

```text

```

```text
merchant_fee_rule_id

route_snapshot_json
psp_id
psp_method_id
psp_account_id

```

```text
payment_plan_version
payment_plan_bucket_id
payment_plan_route_option_id
```

## 编译校验

发布前必须校验：

```text
商户费率是否存在
商户费率金额区间是否重叠
商户费率金额区间是否漏段
PSP路由候选是否存在
PSP Provider 是否启用
PSP Method 是否启用
PSP Account 是否启用
PSP成本费率是否存在
PSP成本费率金额区间是否覆盖
每个 bucket 是否至少有一个 ACTIVE route option
同一个金额是否只命中一个 bucket
```

如果要求 PSP 成本必须实时准确，`psp_fee_rule` 缺失应作为 ERROR 阻止发布。

## 阶段落地

第一阶段：

```text
新增三张表
新增运行时读取 ACTIVE catalog
没有 ACTIVE 时降级旧实时规则
配置变更清 Redis
```

第二阶段：

```text
后台新增测试/预检/发布入口
发布时编译 bucket 和 route option
商户 API 优先读新三张表
```

第三阶段：

```text
增加 PSP 紧急停用 Redis key
支持 route option 自动跳过不可用 PSP
支持 fallback_order 切备用
```

第四阶段：

```text
同 priority 下支持 weight 分流
接入 PSP 健康状态和熔断
```

## 最终推荐

当前最终方案：

```text
旧表不动
新增三张表：
1. payment_plan_catalog
2. payment_plan_bucket
3. payment_plan_route_option
```

职责划分：

```text
catalog       管版本
bucket        管金额区间和商户费率
route_option  管 PSP 候选、优先级、权重、备用和 PSP 成本
```

这比两张表更适合支付系统，因为它能解决：

```text
多个 PSP 支持同一金额段
PSP 故障快速停用
自动切备用 PSP
后续按权重分流
后续健康检测和熔断
```
