有，这种支付/商户/PSP 项目一般一定要做风控。你可以把风控分成 5 层来看，不要一开始就做得特别复杂，先把“能挡住明显风险、能留痕、能人工处理”的基础能力建起来。

**一、商户风控**

这是针对商户本身的控制。

常见规则：

```text
商户状态：正常 / 暂停 / 禁用
商户 API Key 状态
商户 IP 白名单
商户单笔限额
商户每日限额
商户每小时限额
商户可用币种限制
商户可用支付方式限制
商户可用通道限制
商户余额不足限制
商户代付人工审核开关
```

你项目里现在已经有商户、应用、币种、路由、余额这些基础，所以第一阶段很好加。

建议先加：

```text
merchant_risk_config
```

里面放：

```text
merchant_id
app_id
currency
min_amount
max_amount
daily_amount_limit
daily_count_limit
hourly_amount_limit
hourly_count_limit
ip_whitelist
manual_review_enabled
status
```

在这些地方校验：

```text
OpenPayinOrderServiceImpl 创建代收订单前
OpenPayoutOrderServiceImpl 创建代付订单前
OpenApiAuthFilter 签名鉴权后校验 IP 白名单
```

**二、订单风控**

这是针对每一笔订单的控制。

代收常见规则：

```text
金额是否在范围内
币种是否允许
国家是否允许
支付方式是否允许
同一个商户订单号是否重复
短时间内同金额/同用户/同设备重复提交
订单金额是否异常
```

代付常见规则：

```text
单笔金额限制
每日代付总额限制
收款人银行卡/钱包号黑名单
同一个收款账号短时间多笔代付
代付失败次数过多
余额是否足够
是否需要人工审核
```

建议代付比代收更严格，因为代付是真出钱。

代付订单状态可以加：

```text
PENDING_REVIEW   待审核
RISK_REJECTED    风控拒绝
APPROVED         审核通过
```

处理流程：

```text
商户发起代付
-> 参数校验
-> 风控校验
-> 如果命中高风险，进入待审核
-> 后台人工审核
-> 审核通过后再提交 PSP
```

**三、通道风控**

这是针对 PSP / 通道的控制。

常见规则：

```text
通道状态：正常 / 维护 / 禁用
通道单笔限额
通道每日限额
通道成功率过低自动降权
通道连续失败次数过多自动暂停
通道余额不足暂停代付
通道回调异常率过高告警
通道响应超时切换备用通道
```

你项目里已经有路由和 PSP 概念，后面可以加：

```text
psp_channel_risk_config
psp_channel_daily_stats
psp_channel_health
```

路由选择时先过滤：

```text
状态异常的通道
超过限额的通道
余额不足的通道
成功率过低的通道
```

然后再按优先级、权重选择通道。

**四、回调风控**

PSP 回调也要防。

常见规则：

```text
回调签名校验
回调 IP 白名单
订单状态幂等
金额必须和原订单一致
币种必须一致
PSP 订单号必须匹配
成功订单不能被失败回调覆盖
重复回调只返回成功，不重复入账
异常回调记录日志和告警
```

你现在已经讨论过 `/psp/callback/**` 放在 `gk-api`，这里必须重点做。

建议回调处理流程：

```text
接收回调
-> 记录原始报文
-> 校验 PSP 来源/IP/签名
-> 解析订单
-> 校验金额、币种、订单状态
-> 幂等锁
-> 更新订单
-> 入账
-> 发送商户通知
-> 记录回调处理结果
```

**五、系统安全风控**

这是保护接口和后台。

常见规则：

```text
商户 API 签名
timestamp 防重放
nonce 防重复请求
接口限流
登录失败锁定
后台操作审计日志
敏感操作二次确认
管理员 IP 白名单
数据库变更留痕
```

你现在商户 API 只让 `/api/v1/**` 走签名鉴权，这个方向是对的。

建议补：

```text
timestamp 超过 5 分钟拒绝
nonce/requestId 存 Redis，防重复提交
同 appId 每分钟请求数限制
同 IP 每分钟请求数限制
```

**推荐你第一阶段先做这些**

不要一口气做大风控系统。第一版建议先做 8 个最实用的：

```text
1. 商户 IP 白名单
2. 商户单笔限额
3. 商户每日金额限额
4. 商户每日笔数限额
5. 代付余额不足拦截
6. 代付大额人工审核
7. PSP 回调金额/币种/状态幂等校验
8. API timestamp + nonce 防重放
```

**项目中建议加的位置**

```text
gk-merchant
  商户风控配置
  商户 API/IP/限额配置

gk-payment
  订单风控校验
  代收/代付限额
  人工审核状态
  PSP 通道健康度

gk-psp
  PSP 回调签名/IP/金额校验
  PSP 通道状态和余额

gk-openapi
  商户 API 签名
  timestamp/nonce
  API 限流

gk-ledger
  余额检查
  冻结/解冻/扣款一致性
```

**建议的数据表**

可以先设计这几张：

```text
merchant_risk_config
商户风控配置

merchant_risk_daily_limit
商户每日限额统计，也可以先用 Redis

risk_blacklist
黑名单：银行卡、钱包、手机号、IP、商户号

risk_review_order
人工审核单

risk_event_log
风控命中日志

psp_channel_health
通道健康状态
```

**工作流大概是这样**

```text
商户请求创建订单
-> OpenAPI 鉴权
-> 防重放/限流
-> 商户状态校验
-> 商户风控配置校验
-> 订单风控校验
-> 余额/通道校验
-> 命中低风险：继续创建订单
-> 命中中风险：进入人工审核
-> 命中高风险：直接拒绝
-> 记录 risk_event_log
-> 必要时发送 Telegram 风控预警
```

你这个项目我建议下一步先做“商户风控配置 + 代付大额审核 + 风控日志”。这三个一上来最有价值，也不会把系统搞得太复杂。
